# 安装、升级与故障处理

这份说明供首次接触本项目的运维人员使用。你只需上传一个 `.run` 包，在服务器执行一条命令。脚本会检查环境、导入镜像、备份、迁移、启动并报告结果，不需要手工解包或复制配置。

## 先认识三个东西

- **镜像**是程序本体，社区版从源码在本地构建，默认使用公共 npm；操作见源码仓库的 `docs/build.md`。
- **`.run` 包**是送到服务器的安装材料，带镜像和本版本必需的部署文件。
- **环境目录**保存配置、部署记录及备份。应用数据仍使用原来的持久卷，升级不搬迁数据。

测试和正式在同一台主机时，镜像只需导入一次。每个环境各自锁定版本，因此测试换版本不会让正式在下次重建时意外换版。`latest` 仍保留作镜像别名。

## 1. 准备和下载

服务器需为 Linux amd64 或 arm64，具备 Bash、Docker、tar、gzip、SHA256 校验工具和 Docker Compose V2 **2.20 或以上**。首次交互安装还需 openssl。目标用户需有 Docker 和部署目录的操作权限。脚本不会在服务器下载软件或拉取镜像。

先按源码仓库的 `docs/build.md`构建四应用镜像，再从同一提交生成 install/upgrade 两种 `.run` 文件。社区版不要求维护者的 GitLab、Harbor、Nexus 或下载账号。

| 你要做什么 | 下载哪个文件 |
| --- | --- |
| 从未部署过的全新环境 | `ai-dev-insight-版本-amd64-install.run` |
| 已有环境更新应用 | `ai-dev-insight-版本-amd64-upgrade.run` |

arm64 主机选择名称中带 arm64 的包。install 包额外包含数据库镜像；日常 upgrade 包不升级数据库基础组件。本地镜像清单和两种包须分别核验，打包成功不代表服务器部署验收已经通过。

把选中的**一个文件**上传到服务器空间充足、当前用户可写的位置，例如 `/opt/oss-llm/`。不要解包到正在运行的环境目录；`.run` 会自行校验，默认在上传目录临时解包，结束后删除临时文件。需要另选位置时用 `TMPDIR` 指定 Docker 也能看到的目录，避免旧主机的私有 `/tmp`。

下文以 `ai-dev-insight-0123456789ab-amd64-upgrade.run` 举例，实际使用下载文件的名字；示例编号不代表可下载的发行版本。

## 2. 日常升级：先测试，再正式

进入上传文件的目录，在维护窗口执行：

```bash
bash ai-dev-insight-0123456789ab-amd64-upgrade.run upgrade --env test
```

脚本会先显示并核对：

```text
环境：test
目录：/opt/oss-llm/ai-dev-insight-test
目标版本：完整提交编号
```

正式环境对应 `/opt/oss-llm/ai-dev-insight`。没有 `--env` 就不执行，不默认选择正式环境。

脚本按以下顺序工作：

1. 校验包、架构、配置及实际容器/数据卷归属，导入本机缺少的镜像。
2. 合并本版本部署文件与现场设置，检查可用空间和配置；能提前发现的问题在停服前退出。
3. 停止应用写入，数据库保持运行；备份数据库、密钥、cleanup journal 和原配置。
4. 等待数据库就绪，准备持久目录权限，执行迁移与初始化。任一步失败便停止后续步骤。
5. 启动应用，等待健康检查，记录成功版本与备份位置。

目标维护窗口为 5～10 分钟，实际时间取决于数据量、迁移和启动预热；不是固定耗时保证。同一版本已成功运行时，重复命令仅检查健康状态并提示无需升级。

看到“**自动检查通过，待业务验收**”后完成两步：

1. 用管理员账号打开页面并登录，确认页面正常。
2. 使用测试账号的客户端向**测试地址**上报一条新记录，在页面确认对应结果。只看到客户端 HTTP 成功还不够。

通过后执行：

```bash
bash ai-dev-insight-0123456789ab-amd64-upgrade.run upgrade --env prod
```

正式复用本机已有镜像，不重新上传包或拉取镜像。正式升级后仍完成上述业务验收。技术健康检查不替代真实登录、上报和数据结果检查。

## 3. 第一次安装

仅用于没有已有配置、数据或服务的目录；已有环境必须用 upgrade。

```bash
bash ai-dev-insight-0123456789ab-amd64-install.run install --env test
```

按中文提示填写员工访问地址、管理员邮箱和允许注册的邮箱域。脚本自动生成内部密码和 `.env`；管理员初始密码保存在部署目录 `.env` 的 `ADI_ADMIN_PASSWORD` 中，请私下保管，不粘贴到共享群聊或日志。

测试默认 Web 端口 4182、采集检查端口 4187；正式默认分别为 4181、4186。访问地址可用 HTTP 或由现场代理提供的 HTTPS。脚本不配置入口代理或证书。

已确认需要旧 EL7/libseccomp 兼容的主机，首装命令追加 `--web-el7-compat`，仅对 Web 使用现场既有的 `seccomp=unconfined` 例外，保留其他保护；不自动放宽其他容器。已有环境升级会保留该设置，无须再传。独立 Compose 程序不在目标目录时，可用 `--compose-bin /已有程序的绝对路径`。

已有经过审核的私有配置可用于无人值守首装：

```bash
bash ai-dev-insight-版本-amd64-install.run install --env test --config /私有目录/test.env
```

配置格式见仓库 `.env.example`。其中项目名必须与同机其他环境不同；配置按数据读取，不执行其中的命令。额外环境可使用 `--root /绝对目录`，首次安装会核对项目名冲突和端口占用。

## 4. 失败后怎么做

**不要清库、删除数据目录、执行 `down -v`，也不要直接用旧镜像启动迁移后的数据库。**

| 屏幕提示 | 当前状态 | 处理方式 |
| --- | --- | --- |
| 尚未执行停服步骤 | 本次未停止原应用；可能已有上次未完成状态 | 修正提示的问题，使用同一个包重试；必要时先查看 status |
| 备份、迁移或启动失败 | 应用停止，数据库和数据保留 | 查看屏幕给出的私有日志，修正原因，再执行 recover |
| 自动检查通过，业务验收未通过 | 新版本已运行，等待人工判断 | 保留日志与升级前备份，停止正式晋级；不要自动退库 |

继续完成失败的操作：

```bash
bash ai-dev-insight-0123456789ab-amd64-upgrade.run recover --env test
```

**recover 的含义是：用同一个版本继续完成操作，不是把数据库退回旧版本。** 脚本保留完整的升级前备份，重试权限准备、向前迁移和启动；未完成时拒绝换另一个包。备份本身失败时，保留不完整目录并重新备份，不将其标记为可恢复材料。首装失败也使用原 install 包执行 recover，不清空已建立的数据。

查看状态：

```bash
bash ai-dev-insight-0123456789ab-amd64-upgrade.run status --env test
```

日志在环境目录 `logs/`，备份在 `backups/`。只有存在 `.complete` 的目录才是脚本完整写出的备份；摘要正确仍不等于真实恢复已验证。备份内包含敏感配置和凭据密钥，目录权限应为 0700、文件为 0600，并另外复制到受保护的异机存储。

**需要回退数据库时**，由维护人员使用升级前完整备份制定并执行隔离恢复：先保持入口和全部写入者关闭，核验目标、档案及镜像身份，保留当前最新 cleanup journal，恢复后重放删除证明并审核身份权限，验证后显式开放。具体约束与既有工具见 [恢复参考](REFERENCE.md#数据库备份和恢复)。此操作可能丢弃备份后的写入，不由日常升级脚本自动执行。

## 5. 已有部署的接管与目录整理

已有服务使用 upgrade，不执行 install，不改 Compose 项目名，也不搬数据。升级前核对实际运行的项目名、端口、挂载、持久卷、数据库版本及兼容设置；不要根据另一环境的配置推断当前环境。

脚本保留原数据库服务、项目身份、持久卷、端口、资源和兼容设置；遇到额外 Compose 文件或未知设置时在停服前报错。维护人员应保留能重建这些设置的私有配置和升级前备份。

整理规则：保留当前和上一个成功版本及对应备份。先预览并核对候选是否仍被外部脚本使用：

```bash
bash ai-dev-insight-版本-amd64-upgrade.run cleanup --env test
```

确认后在相同命令末尾追加 `--apply`，将已识别的旧镜像压缩包、空配置的旧解包目录和旧导入/导出脚本移入 `archive/`。满 14 天后，再用 `cleanup --env test --purge` 显式删除受管归档。正式环境使用 `--env prod`；自定义环境目录须传入相同的 `--root`。

脚本核对全机容器挂载和持久卷的绑定路径，保护仍被引用的文件/目录。未知文件、含私有密码的旧目录、数据、备份及未受管归档保留；备份超出保留目标时另列清单核实。升级未完成时拒绝整理，不对整台主机执行 Docker 全局 prune。

部署目录保留运行配置、必要脚本、状态记录，以及原数据、备份和日志。上传包放在业务目录之外，不反复堆积解包目录。

数据集隔离与恢复边界见 [高级参考](REFERENCE.md)。普通 upgrade 不替代独立数据集重建。

## 6. 开发和发布人员

社区版不自动发布镜像或上传离线包。先在源码仓库根目录运行 `make images`，再从同一完整提交和目标架构生成两种包：

```bash
revision=$(git rev-parse HEAD)
sh deploy/manual/export-images.sh --local --kind upgrade --tag "$revision"
sh deploy/manual/export-images.sh --local --kind install --tag "$revision"
```

默认本地前缀为 `local/ai-dev-insight`；自定义构建前缀时，导出命令须传入相同的 `--image-prefix`。arm64 构建与导出均须选择 `linux/arm64`。install 使用固定 PostgreSQL 父摘要及所选平台子摘要，打包机沿用 Docker 的网络配置；交付物不复制打包机私有 `.env`。

验证结果分别记录：命令夹具、真实镜像构建、离线包生成、目标环境业务闭环和实际 Trae 设备验收。公开 CI 平台、下载渠道与正式发布另行确定。
